# План A/B-тестирования моделей скоринга

Сравнение двух версий модели прогнозирования дефолта в проде: **v1 (LogisticRegression)** - текущая, **v2 (RandomForest)** - кандидат на замену

---

## 1. Постановка

### Гипотеза

**H0:** качество отбора дефолтёров у v2 не отличается от v1 - разница F1 по классу «дефолт» равна нулю

**H1:** v2 даёт более высокий F1 при неухудшении ожидаемых финансовых потерь банка

### Что именно меняется

Обе модели решают одну задачу и получают одинаковый набор из 23 признаков. Различие только в семействе алгоритмов: линейная модель против ансамбля деревьев. Порог отсечения у обеих 0.5, чтобы сравнение не смешивало два эффекта сразу - смену модели и смену порога

### Единица рандомизации

**Клиент (`client_id`), а не запрос.** Это принципиально: один клиент может обратиться несколько раз, и если группа будет выбираться заново на каждый запрос, он получит разные решения по одной заявке. Помимо того что это некорректно с точки зрения статистики (наблюдения перестают быть независимыми), это прямой репутационный и регуляторный риск - отказ и одобрение по одинаковым данным

Реализация в `app/model_handler.py`:

```python
digest = hashlib.md5(str(client_id).encode()).hexdigest()
bucket = int(digest[:8], 16) / 0xFFFFFFFF
version = "v2" if bucket < AB_TRAFFIC_SPLIT else "v1"
```

Хеширование даёт детерминированное разбиение без хранения состояния: сервис остаётся stateless, любой инстанс за балансировщиком отнесёт клиента в ту же группу. Альтернатива - таблица назначений в БД - потребовала бы синхронизации и добавила точку отказа

### Разделение трафика

**50/50.** Симметричный сплит даёт максимальную статистическую мощность при фиксированном объёме трафика. Доля вынесена в переменную окружения `AB_TRAFFIC_SPLIT`: на старте теста разумно начать с 90/10, убедиться в отсутствии деградации по времени ответа и ошибкам, и только потом выйти на 50/50

### Продолжительность

Считается от требуемого размера выборки, а не «на глаз». Для z-теста долей при α = 0.05 и мощности 80%, база Recall v1 = 0.639:

| MDE по Recall | Дефолтёров на группу |
|---|---|
| ±0.03 | 3 946 |
| ±0.05 | 1 400 |
| ±0.10 | 336 |

Ключевой момент: считать нужно **дефолтёров**, а не все заявки. При доле дефолта 22.1% для MDE = 0.05 нужно 1400 / 0.221 ≈ **6 335 клиентов на группу**, то есть ~12 700 заявок суммарно

При потоке 1 000 заявок в сутки это 13 дней. Округляем до **14 дней** - полное число недель, чтобы в обе группы попал одинаковый набор дней недели. Поток заявок в будни и выходные различается по составу клиентов, и обрыв теста на середине недели смещает оценку

Отдельная сложность этой задачи: **таргет отложен**. Факт дефолта известен только через месяц после решения. Поэтому полный цикл теста - 14 дней набора трафика плюс 30 дней ожидания факта. До этого момента доступны только прокси-метрики (доля отказов, распределение скоров, время ответа), и по ним решение о раскатке не принимается

## 2. Метрики

### Основная

**F1-score по классу «дефолт»**. Классы несбалансированы (22% против 78%), поэтому accuracy бесполезна - модель, отклоняющая всех подряд, покажет 78%. F1 - гармоническое среднее точности и полноты, растёт только когда обе составляющие в порядке

### Дополнительная

**Precision по классу «дефолт»** - доля реальных дефолтёров среди тех, кому отказали

Обоснование выбора именно Precision, а не Recall: цена ошибок несимметрична, но не так, как кажется на первый взгляд. Ложноположительное срабатывание - это отказ платёжеспособному клиенту, то есть упущенная маржа плюс уход клиента к конкуренту. Ложноотрицательное - выданный кредит, который не вернут. При низкой Precision (у v1 это 0.36) банк отказывает двум добросовестным клиентам на каждого пойманного дефолтёра, а доля отказов достигает 37.5% - операционно это неприемлемо: заявки уходят на ручную проверку, и андеррайтинг захлёбывается

### Guardrail-метрики

Метрики, ухудшение которых останавливает тест независимо от основной:

| Метрика | Порог |
|---|---|
| Recall по дефолту | не ниже v1 более чем на 0.05 |
| p99 времени ответа `/predict` | < 200 мс |
| Доля ответов 5xx | < 0.1% |
| Доля отказов (flagged rate) | не выше 40% |

### Бизнес-метрика

**Ожидаемые потери на клиента, NT$.** Технические метрики не отвечают на вопрос «сколько денег это принесёт», а разные типы ошибок стоят по-разному:

| Исход | Смысл | Стоимость |
|---|---|---|
| FN | выдали кредит будущему дефолтёру | `EAD × LGD` |
| FP | отказали платёжеспособному | `EAD × MARGIN` |
| TP | дефолт предотвращён, заявка на ручную проверку | 300 NT$ |
| TN | штатная выдача | 0 |

где `EAD` (exposure at default) - текущая задолженность клиента, в расчёте берётся `BILL_AMT1`; `LGD = 0.6` - доля невозврата при дефолте; `MARGIN = 0.08` - доходность по обслуживаемому долгу. Параметры согласуются с риск-подразделением, здесь взяты типовые для необеспеченного розничного кредитования

Метрика считается поклиентно, поэтому к ней применим t-тест, и её можно пересчитать в годовой эффект на портфель

## 3. Статистический анализ

### Выбор критерия под метрику

| Метрика | Критерий | Почему |
|---|---|---|
| Recall, Precision | двухвыборочный z-тест для долей | это доли; выборки большие, нормальное приближение корректно (np > 30 в обеих группах) |
| F1 | бутстреп, 2000 итераций | F1 - не доля и не среднее, аналитической формулы стандартной ошибки нет |
| Ожидаемые потери | t-тест Уэлча | непрерывная величина, дисперсии групп заведомо разные (хвост крупных задолженностей) |

t-тест Уэлча, а не классический Стьюдента: распределение потерь сильно скошено вправо, требование равенства дисперсий не выполняется

### Доверительные интервалы

- Для долей - интервал Вальда
- Для F1 - перцентильный бутстреп: обе группы ресемплируются с возвращением независимо, разница F1 пересчитывается 2000 раз, границы берутся как 2.5-й и 97.5-й перцентили
- Для денежной метрики - интервал на разность средних через объединённую стандартную ошибку

Везде уровень 95%. Интервал информативнее p-value: он показывает не только «есть ли эффект», но и его правдоподобный размер - а решение о раскатке принимается именно по размеру

### Множественные сравнения

Метрик несколько, поэтому вероятность случайно поймать «значимость» хотя бы в одной выше номинальных 5%. Основная метрика объявлена заранее (F1) и проверяется на α = 0.05; остальные - поправка Холма. Guardrail-метрики проверяются односторонне и без поправки: здесь дешевле ложная тревога, чем пропущенная деградация

### Критерий успешности

v2 раскатывается на 100% трафика, если выполнено **всё**:

1. Нижняя граница 95% ДИ для ΔF1 строго больше нуля
2. Ни одна guardrail-метрика не пробита
3. Верхняя граница ДИ для разницы ожидаемых потерь не превышает +2% от базового уровня (то есть статистически исключён заметный рост потерь)
4. Набран запланированный объём выборки - решение не принимается досрочно

Пункт 4 - защита от «подглядывания» (peeking). Если смотреть на p-value каждый день и останавливаться при первом падении ниже 0.05, фактический уровень ошибки I рода вырастает с 5% до 20-30%. Дата анализа фиксируется заранее; если нужен промежуточный контроль, применяется последовательный дизайн с границами O'Brien-Fleming

### Проверки корректности эксперимента

- **A/A-тест** - сутки, обе группы на v1: если различия «значимы» - сломано разбиение или сбор метрик
- **SRM (sample ratio mismatch)** - χ²-тест фактического соотношения групп против 50/50; расхождение указывает на баг в роутинге
- **Баланс ковариат** - сравнение распределений возраста, лимита и истории платежей между группами

## 4. Результаты пилотного прогона

Прогон на отложенной выборке (6 000 клиентов, моделям не показывалась), разбиение тем же хешем, что в проде: `python scripts/ab_test_analysis.py`.

### Технические метрики

| Метрика | control (v1) | treatment (v2) | Δ |
|---|---|---|---|
| Клиентов | 2 995 | 3 005 | +10 |
| Дефолтов | 629 | 698 | +69 |
| **F1** | 0.4586 | **0.5432** | **+0.0846** |
| Precision | 0.3577 | **0.5000** | +0.1423 |
| Recall | **0.6391** | 0.5946 | −0.0445 |
| Доля отказов | 0.3753 | 0.2762 | −0.0991 |

### Значимость

| Проверка | Результат | 95% ДИ | p-value | Вывод |
|---|---|---|---|---|
| ΔF1 (бутстреп) | +0.0846 | [+0.0429; +0.1239] | - | **значимо** |
| ΔPrecision (z-тест) | +0.1423 | [+0.0983; +0.1864] | < 0.001 | **значимо** |
| ΔRecall (z-тест) | −0.0446 | [−0.0969; +0.0077] | 0.096 | не значимо |

### Бизнес-метрика

| Показатель | Значение |
|---|---|
| Ожидаемые потери на клиента, v1 | 3 277.01 NT$ |
| Ожидаемые потери на клиента, v2 | 3 434.58 NT$ |
| Разница | +157.56 NT$ (+4.81%) |
| 95% ДИ разницы | [−789.19; +1 104.32] |
| p-value (t-тест Уэлча) | 0.744 |
| Эффект на 100 000 клиентов | −15.8 млн NT$ |

### Интерпретация

Результат ровно тот, ради которого бизнес-метрики и вводят: **технически v2 лучше, экономически - не доказано**

F1 вырос значимо, и виновата в этом Precision: доля отказов упала с 37.5% до 27.6%, то есть v2 беспокоит андеррайтинг на треть реже. Но Recall просел на 4.5 п.п. - часть дефолтёров теперь проходит фильтр. И вот здесь вступает в дело асимметрия сумм: пропущенный дефолт стоит `EAD × 0.6`, а лишний отказ - всего `EAD × 0.08`, то есть в 7.5 раза дешевле. Поэтому небольшое снижение Recall съедает весь выигрыш от роста Precision, и средние потери даже растут на 157 NT$ на клиента

При этом разница по деньгам **статистически не подтверждена**: p = 0.74, доверительный интервал широко накрывает ноль. Причина - тяжёлый правый хвост распределения задолженностей: несколько клиентов с крупным `BILL_AMT1` дают такую дисперсию, что 6 000 наблюдений для денежной метрики мало. Для неё потребовалась бы выборка на порядок больше либо винзоризация выбросов

**Решение по критерию из раздела 3:** пункт 1 выполнен (ДИ для ΔF1 не накрывает ноль), но пункт 3 - нет: верхняя граница ДИ по потерям (+1 104 NT$ на клиента) далеко выходит за допустимые +2%. **v2 на полный трафик не раскатывается.**

Рекомендации вместо раскатки:

1. **Подобрать порог v2 по бизнес-метрике, а не оставлять 0.5.** Порог - свободный параметр, и оптимизировать его следует под функцию потерь, а не под F1. Снижение порога вернёт Recall, сохранив часть выигрыша в Precision
2. **Повторить тест на большей выборке** - денежная метрика требует существенно большего n
3. **Винзоризовать `EAD`** на 99-м перцентиле при расчёте метрики, чтобы единичные крупные задолженности не определяли результат

## 5. Связь с архитектурой сервиса

Дизайн теста напрямую определил три решения в коде.

**Роутинг на стороне сервиса, а не балансировщика.** Обе модели загружаются в один процесс (`ModelRegistry` в `app/model_handler.py`), выбор происходит внутри обработчика запроса. Альтернатива - два отдельных деплоя и разделение трафика на NGINX - потребовала бы вдвое больше контейнеров и лишила бы возможности логировать назначение группы рядом с самим предсказанием. Оперативная память расходуется на обе модели сразу (~6 МБ на RandomForest), что при таких размерах несущественно

**Stateless-разбиение по хешу.** Позволяет горизонтально масштабировать сервис: `docker compose up --scale api=3` не ломает эксперимент, все реплики отнесут клиента в одну группу без общего хранилища

**Логирование как источник данных для анализа.** Каждое предсказание пишется в stdout строкой JSON:

```json
{"ts": "2026-08-11T10:18:38.783+00:00", "event": "prediction",
 "request_id": "6d6927d9fd87b8008a5a5095dd3a47bc", "client_id": "client-0042",
 "model_version": "v2", "ab_group": "treatment", "routing": "hash(client_id)",
 "prediction": 1, "probability": 0.77158}
```

Поля `ab_group`, `model_version` и `client_id` - это и есть сырьё для расчёта метрик. В production такой лог собирается Filebeat в Elasticsearch, джойнится по `client_id` с фактом дефолта из хранилища через месяц, и метрики считаются тем же скриптом `scripts/ab_test_analysis.py`. Без этих полей в логе тест пришлось бы восстанавливать по косвенным данным

**Возможность явного выбора версии** (`?version=v2` или поле `model_version`) добавлена для отладки и демонстрации, но в production такой параметр должен приниматься только от внутренних систем - иначе клиент сможет сам выбрать себе модель и разрушит рандомизацию

### Демонстрация на живом сервисе

```bash
python scripts/ab_traffic_demo.py --url http://localhost:5001 --n 200
```

Вывод:


## 3. Статистический анализ

### Выбор критерия под метрику

| Метрика | Критерий | Почему |
|---|---|---|
| Recall, Precision | двухвыборочный z-тест для долей | это доли; выборки большие, нормальное приближение корректно (np > 30 в обеих группах) |
| F1 | бутстреп, 2000 итераций | F1 — не доля и не среднее, аналитической формулы стандартной ошибки нет |
| Ожидаемые потери | t-тест Уэлча | непрерывная величина, дисперсии групп заведомо разные (хвост крупных задолженностей) |

### Доверительные интервалы

- Для долей — интервал Вальда: `Δp ± z₀.₉₇₅ · √(p₁(1−p₁)/n₁ + p₂(1−p₂)/n₂)`.
- Для F1 — перцентильный бутстреп: обе группы ресемплируются с возвращением независимо, разница F1 пересчитывается 2000 раз, границы берутся как 2.5-й и 97.5-й перцентили.
- Для денежной метрики — интервал на разность средних через объединённую стандартную ошибку

Везде уровень 95%. Интервал информативнее p-value: он показывает не только «есть ли эффект», но и его правдоподобный размер — а решение о раскатке принимается именно по размеру

### Множественные сравнения

Метрик несколько, поэтому вероятность случайно поймать «значимость» хотя бы в одной выше номинальных 5%. Основная метрика объявлена заранее (F1) и проверяется на α = 0.05; остальные — поправка Холма. Guardrail-метрики проверяются односторонне и без поправки: здесь дешевле ложная тревога, чем пропущенная деградация

### Критерий успешности

v2 раскатывается на 100% трафика, если выполнено **всё**:

1. Нижняя граница 95% ДИ для ΔF1 строго больше нуля
2. Ни одна guardrail-метрика не пробита
3. Верхняя граница ДИ для разницы ожидаемых потерь не превышает +2% от базового уровня (то есть статистически исключён заметный рост потерь)
4. Набран запланированный объём выборки — решение не принимается досрочно

Пункт 4 — защита от «подглядывания» (peeking). Если смотреть на p-value каждый день и останавливаться при первом падении ниже 0.05, фактический уровень ошибки I рода вырастает с 5% до 20–30%. Дата анализа фиксируется заранее; если нужен промежуточный контроль, применяется последовательный дизайн с границами O'Brien–Fleming

### Проверки корректности эксперимента

- **A/A-тест** — сутки, обе группы на v1: если различия «значимы» — сломано разбиение или сбор метрик
- **SRM (sample ratio mismatch)** — χ²-тест фактического соотношения групп против 50/50; расхождение указывает на баг в роутинге
- **Баланс ковариат** — сравнение распределений возраста, лимита и истории платежей между группами

| Показатель | Значение |
|---|---|

### Интерпретация

Результат ровно тот, ради которого бизнес-метрики и вводят: **технически v2 лучше, экономически — не доказано**

F1 вырос значимо, и виновата в этом Precision: доля отказов упала с 37.5% до 27.6%, то есть v2 беспокоит андеррайтинг на треть реже. Но Recall просел на 4.5 п.п. — часть дефолтёров теперь проходит фильтр. И вот здесь вступает в дело асимметрия сумм: пропущенный дефолт стоит `EAD × 0.6`, а лишний отказ — всего `EAD × 0.08`, то есть в 7.5 раза дешевле. Поэтому небольшое снижение Recall съедает весь выигрыш от роста Precision, и средние потери даже растут на 157 NT$ на клиента

При этом разница по деньгам **статистически не подтверждена**: p = 0.74, доверительный интервал широко накрывает ноль. Причина — тяжёлый правый хвост распределения задолженностей: несколько клиентов с крупным `BILL_AMT1` дают такую дисперсию, что 6 000 наблюдений для денежной метрики мало. Для неё потребовалась бы выборка на порядок больше либо винзоризация выбросов

**Решение по критерию из раздела 3:** пункт 1 выполнен (ДИ для ΔF1 не накрывает ноль), но пункт 3 — нет: верхняя граница ДИ по потерям (+1 104 NT$ на клиента) далеко выходит за допустимые +2%. **v2 на полный трафик не раскатывается.**

Рекомендации вместо раскатки:

1. **Подобрать порог v2 по бизнес-метрике, а не оставлять 0.5.** Порог — свободный параметр, и оптимизировать его следует под функцию потерь, а не под F1. Снижение порога вернёт Recall, сохранив часть выигрыша в Precision
2. **Повторить тест на большей выборке** — денежная метрика требует существенно большего n
3. **Винзоризовать `EAD`** на 99-м перцентиле при расчёте метрики, чтобы единичные крупные задолженности не определяли результат

## 5. Связь с архитектурой сервиса

Дизайн теста напрямую определил три решения в коде

**Роутинг на стороне сервиса, а не балансировщика.** Обе модели загружаются в один процесс (`ModelRegistry` в `app/model_handler.py`), выбор происходит внутри обработчика запроса. Альтернатива — два отдельных деплоя и разделение трафика на NGINX — потребовала бы вдвое больше контейнеров и лишила бы возможности логировать назначение группы рядом с самим предсказанием. Оперативная память расходуется на обе модели сразу (~6 МБ на RandomForest), что при таких размерах несущественно

**Stateless-разбиение по хешу.** Позволяет горизонтально масштабировать сервис: `docker compose up --scale api=3` не ломает эксперимент, все реплики отнесут клиента в одну группу без общего хранилища

**Логирование как источник данных для анализа.** Каждое предсказание пишется в stdout строкой JSON:

```json
{"ts": "2026-08-11T10:18:38.783+00:00", "event": "prediction",
 "request_id": "6d6927d9fd87b8008a5a5095dd3a47bc", "client_id": "client-0042",
 "model_version": "v2", "ab_group": "treatment", "routing": "hash(client_id)",
 "prediction": 1, "probability": 0.77158}
```

Поля `ab_group`, `model_version` и `client_id`  сырьё для расчёта метрик. В production такой лог собирается Filebeat в Elasticsearch, джойнится по `client_id` с фактом дефолта из хранилища через месяц, и метрики считаются тем же скриптом `scripts/ab_test_analysis.py`. Без этих полей в логе тест пришлось бы восстанавливать по косвенным данным.

**Возможность явного выбора версии** (`?version=v2` или поле `model_version`) добавлена для отладки и демонстрации, но в production такой параметр должен приниматься только от внутренних систем — иначе клиент сможет сам выбрать себе модель и разрушит рандомизацию
