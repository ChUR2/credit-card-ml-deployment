# Архитектура сервиса

Документ объясняет, почему сервис устроен именно так, и как он изменился бы при росте нагрузки.

---

## Текущая архитектура

```
                  ┌──────────────────────────────────────────┐
   HTTP/JSON      │            Docker network                │
  ────────────►   │                                          │
                  │  ┌────────────┐      ┌────────────────┐  │
   :80            │  │   NGINX    │─────►│   gunicorn     │  │
                  │  │  reverse   │      │  2 воркера     │  │
                  │  │   proxy    │      │  x 4 потока    │  │
                  │  │ rate limit │      │                │  │
                  │  └────────────┘      │  ┌──────────┐  │  │
                  │                      │  │ Flask    │  │  │
   :5001          │                      │  │ /predict │  │  │
  ────────────────┼──────────────────────┼─►│ /health  │  │  │
   (отладка)      │                      │  └────┬─────┘  │  │
                  │                      │       │        │  │
                  │                      │  ┌────▼─────┐  │  │
                  │                      │  │ Model    │  │  │
                  │                      │  │ Registry │  │  │
                  │                      │  │ v1  v2   │  │  │
                  │                      │  └──────────┘  │  │
                  │                      └───────┬────────┘  │
                  └──────────────────────────────┼───────────┘
                                                 │ stdout
                                                 ▼
                                          JSON-логи → ELK
```

Один контейнер с сервисом, перед ним NGINX. Обе версии модели живут в одном процессе, выбор происходит внутри обработчика запроса.

## Монолит vs микросервисы

### Решение

Для этого проекта выбран **монолит** — единый сервис, содержащий загрузку моделей, валидацию, инференс и A/B-роутинг.

### Как выглядела бы микросервисная альтернатива

Разбиение по границам ответственности дало бы минимум четыре сервиса:

| Сервис | Ответственность |
|---|---|
| API Gateway | Валидация входа, аутентификация, маршрутизация |
| Feature Service | Обогащение признаков из хранилища, препроцессинг |
| Model Service v1 | Инференс LogisticRegression |
| Model Service v2 | Инференс RandomForest |
| Experiment Service | Назначение A/B-групп, хранение назначений |

### Почему монолит здесь уместнее

**Границы сервисов не проходят по границам изменений.** Микросервисы окупаются, когда части системы меняются независимо и разными командами. Здесь всё наоборот: препроцессинг, модель и формат ответа меняются одновременно — при переобучении. Разнеся их по сервисам, мы получили бы обязательство деплоить их синхронно, то есть распределённый монолит с сетевыми задержками, но без выигрыша в независимости.

**Сетевые накладные расходы сопоставимы с полезной работой.** Инференс одной модели занимает единицы миллисекунд. Каждый межсервисный HTTP-вызов добавляет 1–5 мс на локальной сети плюс сериализацию. Цепочка из четырёх сервисов увеличила бы время ответа кратно, ничего не дав взамен.

**Один артефакт вместо согласования версий.** Пайплайн препроцессинга и модель обучаются вместе и обязаны использоваться вместе. В монолите это гарантировано одним `.pkl`-бандлом. В микросервисах пришлось бы отдельно версионировать контракт признаков между Feature Service и Model Service — классический источник рассинхронизации, когда модель ждёт 23 признака в одном порядке, а получает другой.

**Модели маленькие.** v1 занимает 5 КБ, v2 — 5.7 МБ. Держать обе в памяти одного процесса дешевле, чем поднимать два контейнера. Аргумент «микросервисы позволяют масштабировать модели независимо» здесь не работает: нечего масштабировать независимо.

**Стоимость эксплуатации.** Микросервисы требуют service discovery, распределённой трассировки, отдельных пайплайнов CI/CD и мониторинга на каждый сервис. Для команды, эксплуатирующей одну модель, это издержки без отдачи.

### Когда решение следует пересмотреть

Монолит перестанет быть оптимальным при выполнении любого из условий:

| Триггер | Что выделять |
|---|---|
| Модели на GPU или тяжёлые нейросети | Model Service на отдельных нодах с GPU |
| Признаки собираются из внешних источников (транзакции, бюро кредитных историй) | Feature Service с собственным кешем |
| Десятки моделей на разные продукты | Model Registry как сервис (MLflow Model Registry, Seldon) |
| Разные SLA: онлайн-скоринг 50 мс и ночные батчи | Разделение online/offline инференса |
| Разные команды владеют разными частями | Разбиение по командным границам |

Важно, что переход не потребует переписывания: `ModelRegistry` уже изолирован от Flask и может быть вынесен за сетевую границу без изменения логики API.

### Горизонтальное масштабирование монолита

Сервис stateless: не хранит сессии, A/B-группа вычисляется хешем. Поэтому масштабируется репликами:

```bash
docker compose up --scale api=3
```

NGINX распределит нагрузку между репликами, и клиент попадёт в ту же A/B-группу независимо от того, какая реплика его обслужила. Это прямое следствие отказа от хранения назначений в БД.

## Брокер сообщений (концепт)

Сейчас все запросы обрабатываются синхронно: клиент ждёт ответа. Для скоринга одной заявки это правильно — решение нужно немедленно.

Синхронная модель ломается в трёх сценариях, и в каждом помог бы **RabbitMQ**.

### Сценарий 1: батч-скоринг портфеля

Раз в месяц риск-подразделение переоценивает весь портфель — сотни тысяч клиентов. Синхронный HTTP тут не годится: запрос будет выполняться часами, любой таймаут или разрыв соединения потеряет результат.

```
Риск-система ──► queue: scoring.batch ──► N воркеров ──► queue: scoring.results ──► БД
```

Что это даёт:

- **Устойчивость.** Задача остаётся в очереди до подтверждения (`ack`). Упавший воркер не теряет работу — сообщение вернётся в очередь.
- **Эластичность.** Скорость обработки регулируется числом консьюмеров, продюсер об этом не знает.
- **Изоляция нагрузки.** Батч не конкурирует за ресурсы с онлайн-скорингом: разные очереди, разные пулы воркеров.
- **Обратное давление.** Длина очереди — естественная метрика перегрузки и сигнал для автоскейлинга.

### Сценарий 2: асинхронное логирование предсказаний

Каждое предсказание нужно сохранить для последующего анализа A/B и мониторинга дрейфа. Писать в БД синхронно внутри обработчика — значит поставить время ответа `/predict` в зависимость от доступности хранилища.

```
Flask ──► exchange: predictions (fanout) ──┬──► queue: analytics  ──► ClickHouse
                                            ├──► queue: monitoring ──► детектор дрейфа
                                            └──► queue: audit      ──► архив
```

`fanout`-обменник рассылает копию сообщения всем подписчикам. Добавление нового потребителя не требует изменений в коде сервиса — важное свойство для регуляторной отчётности, требования к которой меняются.

### Сценарий 3: переобучение по событию

Детектор дрейфа обнаружил расхождение распределений и публикует событие в `model.retrain`. Пайплайн обучения подхватывает его и запускает переобучение, не будучи связанным с сервисом напрямую.

### Что потребовалось бы в коде

Минимальные изменения: продюсер в `app/api.py` (публикация после ответа клиенту), отдельный контейнер-консьюмер, сервис `rabbitmq:3-management` в `docker-compose.yml`. Реализация в рамках проекта не требуется и не выполнена — описан концепт.

## Логирование и мониторинг

### Что логируется сейчас

Приложение пишет структурированные JSON-строки в **stdout** — одна строка на событие. Это принцип 12-factor app: приложение не управляет файлами и ротацией, а отдаёт поток логов, который забирает среда исполнения.

Реализация — `app/logging_config.py`, класс `JsonFormatter`.

| Событие | Когда | Ключевые поля |
|---|---|---|
| `startup` | Старт процесса | `versions` |
| `model_loaded` | Загрузка каждой модели | `model_version`, `path` |
| `request` | Каждый HTTP-запрос кроме `/health` | `method`, `path`, `status`, `latency_ms`, `remote_addr` |
| `prediction` | Каждое предсказание | `client_id`, `model_version`, `ab_group`, `routing`, `prediction`, `probability` |
| `batch_prediction` | Пакетный запрос | `count` |
| `validation_error` | Ошибка входных данных | `detail` |
| `internal_error` | Необработанное исключение | стектрейс |

Пример:

```json
{"ts": "2026-08-11T10:18:38.783+00:00", "level": "INFO", "logger": "credit_api",
 "message": "prediction", "event": "prediction",
 "request_id": "6d6927d9fd87b8008a5a5095dd3a47bc", "client_id": "client-0042",
 "model_version": "v2", "ab_group": "treatment", "routing": "hash(client_id)",
 "prediction": 1, "probability": 0.77158}
```

Почему JSON, а не текст: логи предназначены для машины. Строку `INFO: predicted 1 with prob 0.77` нельзя отфильтровать по вероятности без парсинга регулярками. JSON индексируется как есть, и запрос «все предсказания v2 с вероятностью выше 0.9 за последний час» становится однострочником.

### Сквозная трассировка

`request_id` генерируется NGINX (`$request_id`), передаётся приложению заголовком `X-Request-ID`, попадает во все связанные записи лога и возвращается клиенту в заголовке ответа. Это позволяет проследить один запрос через все слои — от прокси до предсказания. Если клиент прислал свой `X-Request-ID`, используется он.

### Сбор в production: ELK

```
Контейнер ──stdout──► Docker json-file ──► Filebeat ──► Logstash ──► Elasticsearch ──► Kibana
```

| Компонент | Роль |
|---|---|
| Filebeat | Агент на хосте, читает логи контейнеров, добавляет метаданные (имя контейнера, нода) |
| Logstash | Парсинг, обогащение, маршрутизация по индексам |
| Elasticsearch | Хранение и полнотекстовый поиск |
| Kibana | Дашборды и алерты |

Ротация уже настроена в `docker-compose.yml` (`max-size: 10m`, `max-file: 3`) — без неё логи растут неограниченно и рано или поздно забивают диск. В production драйвер `json-file` заменяется на `gelf` или `fluentd`, чтобы логи уходили в сборщик напрямую, минуя диск.

### Что мониторить

**Технические метрики** (Prometheus + Grafana; endpoint `/metrics` добавляется библиотекой `prometheus-flask-exporter`):

| Метрика | Алерт |
|---|---|
| p50 / p95 / p99 времени ответа `/predict` | p99 > 200 мс |
| RPS по версиям модели | — |
| Доля ответов 5xx | > 0.1% за 5 минут |
| Доля 400 (ошибки валидации) | резкий рост — сломался клиент |
| Статус `/health` | 2 неудачи подряд |
| Потребление памяти | > 80% лимита |

**ML-специфичные метрики** — то, чего нет в обычном веб-сервисе:

| Метрика | Зачем |
|---|---|
| Распределение `probability` по дням | Сдвиг означает дрейф данных |
| Доля положительных предсказаний | Скачок = аномалия во входных данных или деградация модели |
| PSI (Population Stability Index) по каждому признаку | Формальный критерий дрейфа: PSI > 0.2 — тревога |
| Соотношение A/B-групп | Отклонение от 50/50 = баг в роутинге (SRM) |
| Отложенные F1/Precision/Recall | Считаются через месяц, когда известен факт дефолта |

Последний пункт — ключевая особенность ML-мониторинга: **качество модели неизвестно в момент предсказания**. Технический мониторинг покажет, что сервис жив и быстр, но не заметит, что модель перестала работать. Поэтому нужны и прокси-метрики (дрейф), и отложенный расчёт настоящего качества.

## Инструменты MLOps

Ниже — назначение инструментов применительно к жизненному циклу именно этой модели. Реализация в проекте не требовалась.

### DVC — версионирование данных

Git хранит код, но не рассчитан на данные: датасет в 2.8 МБ ещё поместится, а снапшот витрины на несколько гигабайт сделает репозиторий неработоспособным. DVC решает это, храня в git только метафайл с хешем, а сами данные — во внешнем хранилище (S3, GCS, диск).

```bash
dvc add data/raw/UCI_Credit_Card.csv   # создаст data/raw/UCI_Credit_Card.csv.dvc
git add data/raw/UCI_Credit_Card.csv.dvc
dvc push                               # данные уезжают в удалённое хранилище
```

Что это даёт в нашем случае:

- **Воспроизводимость.** Сейчас в репозитории лежат `model_v1.pkl` и `model_v2.pkl`, но проверить, на какой именно выгрузке данных они обучены, невозможно. С DVC коммит однозначно связывает версию кода, версию данных и модель.
- **Пайплайн.** `dvc.yaml` описывает этапы (загрузка → обучение → оценка) и их зависимости. `dvc repro` пересчитывает только то, что изменилось: правка гиперпараметра не приводит к перекачиванию датасета.
- **Откат.** `git checkout <старый-коммит> && dvc checkout` возвращает и код, и данные того периода.

### MLflow — трекинг экспериментов

Сейчас метрики двух моделей лежат в `reports/metrics.json` и перезаписываются при каждом запуске обучения. История экспериментов не сохраняется: сравнить сегодняшний прогон с прошлонедельным нельзя.

MLflow Tracking логирует параметры, метрики и артефакты каждого запуска:

```python
with mlflow.start_run(run_name="rf_depth8"):
    mlflow.log_params({"model": "RandomForest", "max_depth": 8, "n_estimators": 300})
    mlflow.log_metrics({"f1": 0.5456, "roc_auc": 0.7731, "pr_auc": 0.5452})
    mlflow.sklearn.log_model(pipe, "model")
```

Применительно к проекту:

- **Сравнение версий.** UI сопоставляет все прогоны таблицей — видно, какой гиперпараметр дал прирост F1.
- **Model Registry.** Модели получают стадии `Staging` → `Production` → `Archived`. Сервис при старте забирает модель по стадии, а не по пути к файлу — исчезает ручное копирование `.pkl` в репозиторий.
- **Связь с A/B.** Версия из реестра проставляется в лог предсказания, и результат A/B-теста однозначно привязывается к конкретному прогону обучения со всеми его параметрами.

### Как это встроилось бы в наш пайплайн

```
DVC (данные) ──► src/train.py ──► MLflow (метрики + модель)
                                        │
                                        ▼
                            Model Registry: Production
                                        │
                                        ▼
                        ModelRegistry.load_all() в сервисе
```

## Бизнес-метрики

Технические метрики не отвечают на вопрос заказчика «сколько это стоит банку». Предлагаются две.

### 1. Ожидаемые финансовые потери на клиента

Каждый тип ошибки имеет цену, и цены сильно различаются:

| Исход | Событие | Стоимость |
|---|---|---|
| FN | Кредит выдан будущему дефолтёру | `EAD × LGD` |
| FP | Отказ платёжеспособному клиенту | `EAD × MARGIN` |
| TP | Дефолт предотвращён, заявка на ручную проверку | 300 NT$ |
| TN | Штатная выдача | 0 |

`EAD` — сумма под риском (в расчёте `BILL_AMT1`), `LGD = 0.6` — доля невозврата, `MARGIN = 0.08` — доходность.

Расчёт реализован в `scripts/ab_test_analysis.py`. На отложенной выборке: v1 — 3 277 NT$ на клиента, v2 — 3 435 NT$. Метрика сразу переводится в масштаб портфеля: разница даёт −15.8 млн NT$ на 100 000 клиентов.

Асимметрия здесь принципиальна: пропущенный дефолт дороже лишнего отказа в 7.5 раза. Именно поэтому модель с более высоким F1 может оказаться экономически хуже — что и произошло с v2.

### 2. Доля одобренных заявок при фиксированном уровне риска

Обратная постановка: зафиксировать приемлемый уровень потерь и максимизировать одобрения. v1 отклоняет 37.5% заявок, v2 — 27.6%. Каждый процентный пункт снижения отказов — это выручка и доля рынка, при условии что потери не выросли.

Расчёт: подобрать порог каждой модели так, чтобы ожидаемые потери совпадали, и сравнить доли одобрений при равном риске. Это честнее, чем сравнение при фиксированном пороге 0.5, который выбран произвольно.

Подробности и статистика — в [ab_test_plan.md](ab_test_plan.md).

## Оптимизация инференса: ONNX

**ONNX** (Open Neural Network Exchange) — открытый формат представления моделей, независимый от фреймворка. Модель scikit-learn конвертируется в граф вычислений, который исполняется рантаймом ONNX Runtime на C++.

```python
from skl2onnx import to_onnx
onx = to_onnx(pipe, X_train[:1].to_numpy().astype(np.float32))
with open("models/model_v1.onnx", "wb") as f:
    f.write(onx.SerializeToString())
```

Инференс:

```python
import onnxruntime as rt
sess = rt.InferenceSession("models/model_v1.onnx")
pred, proba = sess.run(None, {"X": features.astype(np.float32)})
```

Что это даёт:

- **Скорость.** Исполнение в нативном коде без накладных расходов Python; для линейных моделей и ансамблей типичное ускорение — в 2–5 раз на одиночных запросах.
- **Размер образа.** `onnxruntime` весит около 15 МБ против ~200 МБ у scikit-learn со всеми зависимостями (numpy, scipy). Для нашего образа это заметная экономия.
- **Отвязка от версий.** Сериализованная pickle-модель требует той же версии scikit-learn при загрузке — иначе предупреждения или ошибка. ONNX-граф самодостаточен.
- **Переносимость.** Одна модель исполняется из Python, C++, Java, C#, JavaScript — актуально, если скоринг понадобится встроить в мобильное приложение или Java-бэкенд банка.

Ограничения: конвертируются не все преобразования scikit-learn, кастомные трансформеры требуют ручного описания. Для нашего пайплайна (`StandardScaler` + `OneHotEncoder` + линейная модель или ансамбль) поддержка полная.

**Почему не сделано в проекте:** на текущих объёмах инференс занимает единицы миллисекунд и не является узким местом — время ответа определяется сетью и накладными расходами HTTP. Оптимизация имела бы смысл при переходе на десятки тысяч RPS.

## uWSGI и NGINX в production

### Почему не `flask run`

Встроенный сервер Flask (Werkzeug) — инструмент разработки. Он однопоточный по умолчанию, не переживает падение обработчика, не умеет управлять пулом процессов и при запуске сам предупреждает: *"This is a development server. Do not use it in a production deployment."*

### Роль WSGI-сервера (uWSGI / gunicorn)

WSGI — стандартный интерфейс между веб-сервером и Python-приложением. uWSGI и gunicorn реализуют его и берут на себя:

- **Пул воркеров.** Python-процесс ограничен GIL и обрабатывает один запрос за раз. Несколько процессов используют все ядра CPU.
- **Управление жизненным циклом.** Мастер-процесс перезапускает упавшего или зависшего воркера, поддерживая доступность сервиса.
- **Тайм-ауты.** Запрос, выполняющийся дольше лимита, принудительно прерывается и не блокирует воркер навсегда.
- **Graceful reload.** Обновление кода без обрыва активных соединений.

В этом проекте используется **gunicorn** (`docker/Dockerfile`):

```
gunicorn --bind 0.0.0.0:5000 --workers 2 --threads 4 --timeout 60 app.api:app
```

Выбран вместо uWSGI как более простой в настройке при сопоставимой производительности для Python-приложений; uWSGI выигрывает в гибкости (поддержка нескольких языков, тонкая настройка), но его конфигурация заметно сложнее. Формула числа воркеров — `2 × CPU + 1`; здесь взято 2 воркера по 4 потока с учётом того, что каждый процесс держит копию моделей в памяти.

### Роль NGINX

NGINX ставится перед WSGI-сервером и закрывает то, чем приложению заниматься не следует:

| Функция | Зачем |
|---|---|
| Терминация TLS | Сертификаты и шифрование вне Python-кода |
| Буферизация запросов и ответов | Медленный клиент не занимает дорогой воркер gunicorn: NGINX принимает запрос целиком и отдаёт его приложению разом. Прямая защита от slowloris-атак |
| Балансировка нагрузки | `upstream` распределяет трафик между репликами сервиса |
| Rate limiting | В нашем конфиге 20 rps на IP с всплеском до 40 |
| Отдача статики | Файлы не проходят через Python |
| Единый access-лог | Общий формат для всех сервисов, независимо от языка |
| Ограничение размера тела | `client_max_body_size 2m` отсекает мусорные запросы до приложения |

Конфигурация — `docker/nginx/nginx.conf`, поднимается через `docker compose up`.

### Итоговая цепочка

```
Клиент ──HTTPS──► NGINX ──HTTP──► gunicorn ──WSGI──► Flask ──► Model
        TLS,             буферизация,      пул         роутинг,   инференс
        rate limit       балансировка      процессов   валидация
```

Каждый слой решает свою задачу, и ни один не дублирует соседний.
